# 智能笔记升级方案：从"流水账"到"知识产物"（v4）

## 一、核心思路

**阶段1（分块）做重度整理——把每个块整理到位；阶段2（全局）只做轻调——梳理逻辑和结构微调。**

参考 `examflow_runner.py` 的成功经验和你的实际使用反馈，核心策略是：

- **阶段1（分块）**：对每块 ASR 原文做完整的知识提取——去口水话、切分知识点、保留完整推理过程和定义公式。每个块出来就是一份可用的笔记。
- **阶段2（全局）**：不做二次压缩，只做结构调整——调整标题和整体方向、梳理块与块之间的逻辑、拼凑与拆解、把控全局方向。同时新增 `考试核心总览`、`老师强调注意点`、`例题与方法` 三个结构化区块。

**关键原则：阶段1就把内容整理好，阶段2只做微调，不把压力压给全局。**

---

## 二、三个关键问题的决策

### 2.1 原文处理：不保存、不嵌入、不另存文件

**决策：原文直接丢弃，不写入笔记，不另存文件，不保存在内存。**

- 原文的作用是"查流水账"，但智能笔记整理得足够详细准确后不需要再看原文
- 不需要额外找文件存原文，也不需要保存在运行内存里

**代码改动**：在 `runBatchAnalysis()` 和 `runGlobalCorrectionAnalysis()` 中，删除所有 `matchedRaw` 的收集和 `> [!quote]- 📜 原文` 的写入逻辑。

### 2.2 搜索工具：删除

**决策：删除"🔍 搜索转写原文"命令和 `TranscriptionSearchModal`。**

**代码改动**：
- `main.ts` 中删除 `TranscriptionSearchModal` 的导入和"🔍 搜索转写原文"命令注册
- `src/index.ts` 中删除 `export * from './search-modal'`
- `restoreCalloutFolds` 相关的 Ctrl+S 和文件修改监听逻辑也一并清理

### 2.3 分块与全局的职责分工（核心）

**阶段1（分块）= 重度整理，阶段2（全局）= 轻调微调**

| | 阶段1（分块） | 阶段2（全局） |
|---|---|---|
| **定位** | 主力整理阶段 | 辅助微调阶段 |
| **做什么** | ① 去口水话 ② 切分知识点条目 ③ **完整的知识提取**——保留推导过程、定义、公式、例题题意、易错点 ④ 处理截断（片尾传递） | ① 调整标题和整体方向 ② 梳理块间逻辑 ③ 拼凑与拆解（合并同概念、拆分混在一起的不同知识点） ④ 生成考试核心总览 ⑤ 提取老师强调注意点 ⑥ 提取例题方法 |
| **不做什么** | 不压缩知识内容 | **不做二次压缩，不丢信息** |
| **输出质量** | 每个块出来就是一份可用的笔记 | 在阶段1基础上做结构微调 |

### 2.4 片尾衔接机制：保留现有设计

当前已有 `pendingLeftoverRawText` 机制——阶段1 LLM 把被截断的片尾内容放在 `===LEFTOVER===` 块中，代码将其保存到 `this.pendingLeftoverRawText`，下一批次时拼接为 `[上一批次截断内容]\n{leftover}\n\n[本批次内容]\n{currentRaw}` 传给 LLM。

**这个机制完全符合要求，保持不变。**

## 三、数据量分析

### 3.1 实测数据（10.5 分钟课程）

| 项目 | 数值 |
|------|------|
| ASR 原文字符数 | 6,236 |
| summary（阶段1输出）字符数 | 902 |
| 原文占比 | 87.4% |
| 压缩率 | 阶段1将原文压缩到约 14.5% |
| 知识点数量 | 6 |

### 3.2 2 小时课程推算

| 项目 | 数值 |
|------|------|
| 预计阶段1输出（summary 拼接） | ~10,000 字符（约 6,000-7,000 tokens） |
| 预计知识点数量 | ~69 |
| 分块数（10分钟/块） | 12 |

### 3.3 结论

- 阶段1输出的 summary 总量约 1 万字符，传给全局阶段约 6-7K tokens
- DeepSeek V4 Pro 上下文窗口 128K tokens
- **全局阶段完全在 LLM 的舒适区内（<1 万 tokens），不会有"吃不下"或"厚此薄彼"的问题**
- 关键前提：阶段1做的是知识提取（不是只去口水话），输出的是高密度知识要点

#### 5.2.1 阶段1 Prompt（`getBatchSummary`）— 微调

当前 prompt 已经在做知识提取，整体框架不变。微调点：

**改动1：summary 字段描述去掉"精炼"**

```
当前：
summary: 详细记录：使用要点堆叠的方式列出推导步骤、题意条件、结论或解题思路。不要有没营养的虚词，详尽但精炼

summary: 详细记录：使用要点堆叠的方式列出推导步骤、题意条件、结论或解题思路。去掉口水话和没有营养的虚词，但保留所有知识信息，不要为了简短而丢失细节

**改动2：增加 key_points 输出格式**

将 summary 从单个字符串改为 key_points 数组，让 LLM 更自然地输出结构化要点：

```

===SEGMENT===
timestamp: MM:SS
title: 具体知识名 或 例题名
key_points:
- 要点1（完整的推导步骤、定义条件或结论）
- 要点2
- 要点3（数量根据内容自然决定，不要干瘪的短句，也不要强行凑数）
===END===

===LEFTOVER===
这里放末尾被截断的原始转写片段（如果完整则留空）
===END===
```

**改动3：system prompt 微调**

```
当前：

#### 5.2.2 阶段2 Prompt（`getGlobalCorrectionSummary`）— 重写

**核心改动：从"精炼导读重组"改为"轻调微调"——只做结构调整，不压缩信息。**

```
目标：基于所有分片的初步笔记，进行**全局结构微调**。
输入：由分块阶段生成的详细知识点笔记。
输出：微调后的最终知识结构（使用标记格式，不要输出 JSON）。

**核心要求（轻调微调，重点是结构调整，不压缩信息）：**
1. **信息保全第一**：输入中所有知识点、定义、公式、定理、推导过程、例题题意都必须在输出中保留。你可以重新组织语言和调整顺序，但不能丢弃知识内容。
2. **合并与拆分**：合并被时间切片硬性切断的同一知识点；拆分被揉在一起的不同知识点。只有在被时间切片硬性切断的同一句话或同一种解题过程才需要合并。如果内容已经是新题型、新知识点，务必切分成新的章节条目。
3. **调整标题和方向**：使标题更具体、更符合知识点实际内容。把控全局方向的统一性。
4. **梳理逻辑**：确保各知识点之间的逻辑顺序通顺，衔接自然。
5. **key_points 详实**：每个知识点的 key_points 要包含具体的推导步骤、定义条件、关键结论。不要只写概括性描述，要有可以拿去背诵的实质内容。
6. **保留公式定理**：所有数学公式必须使用 LaTeX 语法，用行内 $...$ 包裹。
7. **时间顺序**：按时间戳从小到大排列，保留原始时间戳。

输出格式（严格使用以下行首标记，每行一个字段，不要使用 JSON）：
===SEGMENT===
timestamp: MM:SS
title: 具体的知识点/例题标题
key_points:
- 要点1（详细的推导步骤、定义条件或结论）
- 要点2
- 要点3
===END===

（可以有多个 ===SEGMENT===...===END=== 块）

===META===
exam_focus: 用自然流畅的一段话概括本课核心内容，帮助快速回顾。涵盖老师讲过的所有主要知识点和考试重点。
emphasis: 老师口头强调的注意点1 | 注意点2 | 注意点3（用 | 分隔多个注意点）
examples: ===EX===timestamp|例题标题|解题方法===END=== ===EX===timestamp|例题标题|解题方法===END===
===END===

### 分块笔记列表（请进行结构微调，保留所有知识细节）
${preliminarySummaries}
```

## 七、风险与注意事项

1. **`key_points` 解析**：`key_points` 是多行 `- 要点` 格式，需要在 `parseSegmentFormat` 的多行字段逻辑中处理，将其解析为字符串数组而非单个字符串
2. **`===META===` 解析**：需要扩展 `parseSegmentFormat` 来解析新的 `===META===` 块，包括 `exam_focus`、`emphasis`（按 `|` 分割）、`examples`（按 `===EX===` 分割）
3. **LaTeX 保护**：新增的 `key_points` 字段也需要经过 LaTeX 保护器处理
4. **向后兼容**：`ChapterSummary` 的 `summary` 字段保留，`key_points` 为可选字段，确保阶段1输出仍可使用
5. **`pendingLeftoverRawText`**：截断文本传递机制不受影响，仍保留在内存中（这是 ASR 原文传递给下一批次用的，不是给用户看的）
6. **思维导图跳转**：思维导图中的跳转链接依赖笔记中的 `#### ⏱️ MM:SS 标题` 格式，改造后仍保持此格式
7. **片尾衔接**：`pendingLeftoverRawText` 和 `[上一批次截断内容]` 拼接机制保持不变

## 八、v4 新增：笔记详细程度、思维导图输入与 Prompt 优化

### 8.1 笔记详细程度定位：考研背诵级

**背景**：用户是考研备考场景。政治、英语语法等科目的笔记，看完视频后可能不再回看视频，只看笔记。因此需要"拿去就能背"的详细程度，但又不能变成流水账而失去总结的意义。

**定位标准**：

| 维度 | 标准 |
|------|------|
| **知识定义** | 完整保留——定义、条件、适用范围不能省略 |
| **推导过程** | 保留核心步骤链，省略中间反复试探的过程 |
| **公式定理** | 完整保留，用 $LaTeX$ 包裹 |
| **例题题意** | 保留题目条件和求解目标，省略老师板书细节 |
| **易错点/强调** | 完整保留——这是考试价值最高的部分 |
| **口语废话** | 全部剔除（"同学们看黑板"等） |

**一句话**：**看完笔记能直接去背诵和做题，不需要回看视频。但仍然是一份结构化笔记，不是逐字稿。**

**对阶段1 Prompt 的指导**：
- 当前 `getBatchSummary` 的 prompt 已经在要求详细提取，方向正确
- `key_points` 的每个要点应具有"可背诵的实质内容"，不是笼统的概括
- 但不要求逐字保留——目标是"高密度知识笔记"，不是"原文复述"

**对阶段2 Prompt 的指导**：
- `getGlobalCorrectionSummary` 的 prompt 仍坚持"信息保全第一、不二次压缩"原则
- 但允许微调措辞——把不够精炼的表述收紧，把遗漏的关联补上

### 8.2 思维导图：输入数据改造

**当前问题**：
- 思维导图 prompt 接收 `ChapterSummary[]`，只用 `timestamp | title | summary` 三个字段拼接
- 改造后 `summary` 将被 `key_points` 替代，需适配
- 原始输入中不再包含 ASR 原文（符合用户要求）

**改造方案**：

```typescript
// 之前（line 934）
${chapters.map(c => `[${c.timestamp}] ${c.title} | ${c.summary}`).join('\n')}

// 之后
${chapters.map(c => {
  const detail = c.key_points 
    ? c.key_points.map(kp => `  - ${kp}`).join('\n')
    : c.summary;
  return `[${c.timestamp}] ${c.title}\n${detail}`;
}).join('\n\n')}
```

**关键点**：
- 直接使用 `key_points` 作为思维导图的输入内容
- 不再传 ASR 原文（也不需要，因为 key_points 已经是高质量的知识提取）
- 思维导图基于"整理完之后的笔记内容"生成，而非原始转写文本

### 8.3 思维导图 Prompt 优化：抑制"过度合并"

**当前问题**：用户反馈"之前生成的思维导图总是有些乱，总结得有点过火，把一些没必要合在一起的内容合在一起了"。

**根因分析**：
1. 当前 prompt 中"结构化总结"和"逻辑递进"的措辞引导 LLM 倾向于合并和归纳
2. temperature=0.5 偏高，增加了创造性合并的倾向
3. 缺少"不要过度合并"的负面约束

**改造方案**：

#### 改动1：Prompt 增加过度合并抑制指令

在 `## 核心任务与定位` 中新增：

```
7. **尊重原始切分（重要）**：输入数据中的每个章节已经是一个独立的知识点。你的任务是把它们组织成树状结构，**而不是把不同的知识点强行合并成一个大节点**。
   - 可以按学科逻辑分组（如"概念基础"、"计算方法"、"例题"），这是组织层次的合并
   - 但**不要把不同知识点的具体内容揉进同一个叶子节点**
   - 每个原始知识点在思维导图中都应该有自己独立的分支
   - 简单说：你可以加"文件夹"把文件归类，但不要把文件内容混在一起
```

#### 改动2：温度调低

```typescript
// 之前
stream: false,
temperature: 0.5,

// 之后
stream: false,
temperature: 0.3,  // 降低创造性，提高结构保真度
```

#### 改动3：输出格式示例微调

当前示例中 `## 🎯概念基础` 和 `## 📐计算方法` 是一级分组节点，`### [时间戳]` 是二级知识点节点。这个结构本身是对的——它体现了"加文件夹归类"但不"混内容"的理念。

保持示例不变，但增加一段反例说明：

```
🔴 错误示范（禁止这样做）：
## 🎯概念基础
### [00:00] 极限与洛必达
- 极限定义和洛必达法则混在一起  ← 错误！两个独立知识点被强行合并

✅ 正确做法：
## 🎯概念基础
### [00:00] 极限定义
- 核心思想
  - 描述函数在某一点的趋近行为
## 📐计算方法
### [08:00] 洛必达法则
- 适用场景
  - 专门处理 0/0 型和 ∞/∞ 型未定式
```

#### 改动4：System Prompt 微调

```typescript
// 之前
{ role: "system", content: "You are a mindmap outline generator. Output pure Markdown. NEVER output HTML tags. Keep nodes structured, logical, and easy to understand using concise but meaningful phrases. 请使用中文输出内容。专业术语可保留英文原文，但整体表述应以中文为主，避免大段英文。" }

// 之后

```

### 8.4 思维导图总结尺度把握

用户说"也不要搞得太死板"——这意味着需要在两个极端之间找平衡：

| 太松（过火） | ✅ 合适 | 太死板 |
|------|------|------|
| 把不同知识点内容混在一起 | 按学科逻辑分组，每个知识点有独立分支 | 每个知识点完全独立，没有任何组织结构 |
| 总结性文字过多，像缩写版笔记 | 节点是精炼短语，一眼看懂含义 | 节点就是标题复制粘贴 |
| 把多个例题合成一个 | 例题可以归类到"例题与方法"组下 | 每个例题单独挂在外面 |

**核心原则**：
- **组织层面可以合并**（按主题分组）
- **内容层面不能合并**（不同知识点的要点不能混在一起）
- **节点语言要精炼但表意完整**（不是缩写，不是复制原文）

## 九、思维导图 Rich 模式转换优化

### 9.1 问题

当前 `autoConvertToRich()` 的流程是：
1. 用 `getLeaf(true)` 打开一个新 tab（**会切换用户当前视图**）
2. `setActiveLeaf(leaf, { focus: true })` 显式激活（**再次干扰用户焦点**）
3. 等待 frontmatter 解析 + view 切换为 mindmapview（0-3 秒延迟）
4. 执行 `obsidian-markmind:Change basic mode to rich mode` 命令
5. 轮询等待 rich 文件生成（最多 30 秒）
6. 删除 basic 文件

**用户痛点**：步骤 1-2 会突然切换到思维导图视图，干扰用户正在做的工作。步骤 3 的等待时间让用户被迫停下来等。

### 9.2 约束分析

MarkMind 的 `Change basic mode to rich mode` 命令回调：

```js
callback: () => {
    const t = this.app.workspace.getActiveViewOfType(nN);
    t && t.basicToRich()
}
```

**三个硬约束**：
1. `getActiveViewOfType(nN)` 必须返回一个 MarkMind 的 mindmapview——**必须是当前活动 leaf**
2. `basicToRich()` 内部直接读 `this.mindmap.getData()`——**mindmap 实例必须已渲染完成**
3. `this.mindmap` 是 markmap 库解析 Markdown 后构建的树结构——**需要文件已打开且渲染完毕**

**不可能绕过的原因**：
- `getActiveViewOfType` 只认活动 leaf，后台 leaf 不行
- 不打开文件 → 没有 mindmapview → `getActiveViewOfType` 返回 null → 命令静默 no-op
- `basicToRich` 读的是运行时渲染数据，不是直接读文件内容

**结论：必须打开 basic 文件、必须激活为活动 leaf、必须等渲染完成。这是 MarkMind 架构决定的，无法绕过。**

### 9.3 可行方案：最小化干扰的"快速闪现"策略

既然无法完全避免打开+激活，那就**尽量缩短干扰时间、并在转换完成后立即恢复用户原视图**。

#### 改造方案

```typescript
async autoConvertToRich(basicPath: string, videoDir: string, videoBasename: string) {
    const richPath = basicPath.replace(/\.md$/, '-rich.md');
    
    // 保存用户当前活动 leaf，转换完成后恢复
    const originalActiveLeaf = this.app.workspace.getActiveViewOfType(
        // 保存当前活动 leaf 引用
    )?.leaf;
    
    try {
        // ... 删除旧 rich、等待 frontmatter 等前置逻辑不变 ...

        // 🔑 改动1：用 getLeaf(true) 打开但不调用 setActiveLeaf
        // Obsidian 的 openFile 本身会激活该 leaf
        // 但我们可以用更轻量的方式——打开后立即记录，不额外 focus
        const leaf = this.app.workspace.getLeaf(true);
        await leaf.openFile(basicFile);
        // 不再调用 setActiveLeaf(leaf, { focus: true })
        // openFile 已经把它设为活动 leaf 了
        await sleep(300);
        
        // ... setViewState 兜底逻辑不变 ...
        // ... 执行命令、轮询 rich 文件逻辑不变 ...

        // 🔑 改动2：转换成功后，立即恢复用户原视图
        if (originalActiveLeaf) {
            this.app.workspace.setActiveLeaf(originalActiveLeaf, { focus: true });
        }
        
        // 🔑 改动3：关闭 basic 文件的 leaf（它已经被删了，leaf 是空的）
        // leaf.detach() 可以安全关闭
        leaf.detach();
    } catch (error) {
        // 出错时也要恢复原视图
        if (originalActiveLeaf) {
            this.app.workspace.setActiveLeaf(originalActiveLeaf, { focus: true });
        }
        // ...
    }
}
```

#### 核心改进点

| 改动 | 效果 |
|------|------|
| 去掉 `setActiveLeaf(focus: true)` | `openFile` 已经激活了 leaf，不需要额外 focus |
| 保存并恢复原活动 leaf | 转换完成后立即跳回用户原来在看的内容 |
| `leaf.detach()` 关闭空 leaf | 不留下一个空 tab |
| 整个过程在一个 async 函数中 | 用户看到的只是一个短暂的"闪现"——思维导图 tab 弹出一下就消失 |

#### 预期用户体验

- **之前**：思维导图视图弹出，用户被强制切换，需要等 3-30 秒，然后还要手动切回去
- **之后**：思维导图视图"闪现"一下（约 1-5 秒），然后自动跳回用户原来的视图。用户可能只是看到 Obsidian 界面闪了一下

### 9.4 备选方案：延迟转换（如果闪现也不可接受）

如果"闪现"仍然干扰用户，可以考虑**延迟转换**策略：

- 生成 basic 思维导图文件后，**不立即转换 rich**
- 给 basic 文件打一个 frontmatter 标记 `todo-rich: true`
- 注册一个 `onLayoutReady` 钩子：当用户下次自然打开这个 basic 文件时，检测到 `todo-rich` 标记，自动执行转换
- 优点：完全不干扰用户
- 缺点：basic 文件会在 vault 中存在一段时间，用户打开时才会转换

**但这个方案有风险**：用户可能不会主动打开 basic 文件，导致 rich 模式永远不会生成。

### 9.5 推荐

**推荐 9.3 的"快速闪现"策略**——它满足 MarkMind 的硬约束，同时最小化干扰。用户体验从"被强制切换并等待"变为"界面闪一下就回来"。

如果后续反馈仍然不可接受，再考虑 9.4 的延迟转换作为降级方案。
