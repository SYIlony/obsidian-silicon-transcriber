## 三、当前已排除的假设

### 3.1 「SSE 数据串流」假设（已排除）

**假设内容**：批次 2 的 `requestDirect` 调用收到了全局校验请求的 SSE 数据。

**排除证据**：

1. **代码层面无共享状态**：
   - `http-direct.ts` 每次调用创建独立的 `http.Agent`、独立 Promise、独立闭包变量
   - `llm.ts` 的 `sseContent`/`sseReasoning`/`chunkCount` 是 `let` 局部变量，每次 `for` 循环重新声明
   - `onSSEData` 回调是闭包，只写入自己的变量

2. **数据层面不匹配**：
   - 批次 2 的 content 是正常的 `===SEGMENT===` 格式（timestamp: 07:00，title: 例题9.26），不是全局校验的 `===META===` 格式
   - 数字不匹配：批次 2 = 22268 chunks，全局第 1 次 = 19132 chunks，全局第 2 次 = 17076 chunks，无加法关系

### 3.2 「Gateway 信号量阻塞」假设（已排除）

- Gateway 的 `MAX_CONCURRENT_REQUESTS = 10`，最多 7 个并发批次请求，不会到 10
- `call_log.json` 显示所有请求都立即开始（`status="streaming"`），没有排队

### 3.3 「Gateway 日志显示 1-2 秒所以很快」假设（已排除）

- Gateway 的 HTTP 中间件（`ollama_proxy.py` L68-86）在 `call_next` 返回后就记录 duration
- 对于 `StreamingResponse`，`call_next` 返回时只是 HTTP 响应头已发送，流式 body 还在传输
- **Gateway 日志里的 1-2 秒是假象，不是流完成时间**

## 四、当前未排除的假设（需要进一步验证）

### 4.1 「模型对批次 2 的内容产生了极长 reasoning」假设

**支持证据**：
- 批次 2 的 reasoning = 51505 字符，是第二高（批次 5 的 8731）的 6 倍
- SSE chunks = 22268，是第二高（批次 5 的 6401）的 3.5 倍
- 批次 2 的 content 是正确的批次分析结果（4 个 segments，例题9.26）
- 平均每 chunk 2.5 字符，属于正常的流式 token 输出

**疑问**：
- 如果是模型内容导致的，为什么「每次都是批次 2 最慢」？如果每次视频内容不同，不应该总是位置第 2 的最慢
- 需要验证：是「内容恰好复杂」还是「位置 2 本身有问题」

### 4.2 「火山引擎同 key 并发排队」假设

**支持证据**：
- `volc_handler.py` 有 3 个 key，轮询策略
- 4 个并发批次请求中，可能有 2 个用同一个 key
- 火山引擎可能对同 key 的并发请求排队处理

**需要验证**：
- 查看 Gateway 的 `print` 输出（stdout），确认每个请求实际用了哪个 key
- `call_log.json` 中 05:18:32 有 3 条 `glm-5-2-260617` + `ark-57fe...`（同一 key），说明确实有同 key 并发

### 4.3 「OpenAI SDK timeout=120s 导致流中断后重试」假设

**关键代码**：`volc_handler.py` L256-262
```python
def build_volc_client(key: str) -> AsyncOpenAI:
    return AsyncOpenAI(
        base_url=VOLC_BASE_URL,
        api_key=key,
        timeout=120.0,   # ← 这是整体超时，对流式请求是 chunk 间 read timeout
        max_retries=0,
    )
```

- OpenAI Python SDK 的 `timeout=120.0` 会被 httpx 解释为所有阶段都是 120s
- 对流式请求，read timeout = 两个 chunk 之间的最大间隔 = 120s
- 只要火山引擎每 120s 内发一个 chunk，就不会超时
- **但如果模型在 reasoning 阶段某个 chunk 间隔超过 120s，SDK 会超时**
- SDK 超时后，`stream_wrapper.py` 的 `async for chunk in sdk_stream` 抛异常，`finally` 执行 `client.close()`
- 此时 `yield "data: [DONE]\n\n"` 不会被执行，插件的 `res.on('end')` 触发 resolve
- **但插件日志显示批次 2 收到了 `[DONE]` 并正常返回，所以这个假设可能不成立**

**需要验证**：
- 在 Gateway 的 `stream_wrapper.py` 加上流式完成时间日志和异常日志
- 确认 SDK 是否有过超时

4. 如果 call_log 条数 > 插件日志条数，说明有模型 fallback 或重试

1. 运行多次不同的视频转写
2. 记录每次哪个批次最后完成
3. 如果总是位置第 2 个最后 → 可能是并发/调度问题
4. 如果总是内容最复杂的那个最后 → 是模型行为

```python
def safe_stream_response(sdk_stream, client, on_tokens=None):
    total_tokens = 0
    start_time = _time.time()
    chunk_count = 0

    async def sse_generator():
        nonlocal total_tokens, chunk_count
        try:
            async for chunk in sdk_stream:
                chunk_count += 1
                # 每 1000 个 chunk 打一次日志
                if chunk_count % 1000 == 0:
                    print(f"  [Stream] {chunk_count} chunks, {_time.time() - start_time:.1f}s")
                # ... 原有逻辑
            yield "data: [DONE]\n\n"
            print(f"  [Stream] ✅ 完成 | chunks={chunk_count} | duration={_time.time() - start_time:.1f}s | tokens={total_tokens}")
        except Exception as e:
            print(f"  [Stream] ❌ 异常 | chunks={chunk_count} | duration={_time.time() - start_time:.1f}s | error={e}")
            raise
        finally:
            print(f"  [Stream] finally | chunks={chunk_count} | duration={_time.time() - start_time:.1f}s")
            if on_tokens:
                on_tokens(total_tokens)
            await client.close()

    return StreamingResponse(...)
```

## 九、已知的真实 Bug（独立于批次 2 问题）

### 9.1 `pendingLeftoverRawText` 并发竞态

文件：`main.js` L3947-3952, L4008-4010

```javascript
// L3947: 读取（在 runBatchAnalysis 中）
let rawText = this.pendingLeftoverRawText ? `...` : "";
this.pendingLeftoverRawText = "";

// L4008: 写入
if (currentLeftover) {
    this.pendingLeftoverRawText = currentLeftover;
}
```

多个并发 worker 同时执行 `runBatchAnalysis`，会竞态读写 `this.pendingLeftoverRawText`。可能导致：
- 某个批次的 leftover 被另一个 worker 读取后清空，真正的下一个批次拿到空值
- 某个批次的 leftover 被另一个 worker 的写入覆盖

这不直接导致批次 2 延迟，但会导致**内容上下文断裂**。

### 9.2 Gateway 流式请求时间记录错误

文件：`ollama_proxy.py` L68-86

HTTP 中间件对 `StreamingResponse` 只记录响应头发送时间，不记录流完成时间。需要改用 ASGI 中间件或在 `stream_wrapper.py` 中记录。

### 9.3 全局校验超时 300s 可能不够

文件：`llm.ts` L1059

全局校验 prompt 17909 字符，模型 reasoning 可达 26819 字符。300 秒硬性超时导致无谓重试。建议提到 600s 或改为只重试不超时。
